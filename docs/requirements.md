> - 새 ID: `PF-`(기능) · `PN-`(비기능·안전). §1~§9 의 기존 ID 는 코드 주석·마이그레이션이 인용하므로

> - 괄호 안 `기획 6-1` 등은 기획 변경 설명서(2026-09-23, 사용자 제공·저장소 밖)의 절 번호,
>   `D5`·`W1` 등은 파일럿 계획의 항목 번호다.

### 0-1. 검증 가설과 조건

- **가설**: AI 가 진행한 1:1 회상 대화 세션 1회가 **공단 형식 인지활동 프로그램 1회**로 기록되는가 —
  세션 종료 → 일지 초안 자동 생성 → 사람이 확인·확정 → (선택) 보호자 공개.
  그리고 요양보호사 1명이 여러 기기의 세션을 **감독 화면**으로 지켜보는 병렬 운영이 현장에서 작동하는가.
- **조건**: 1기관 · 동시 2~4대 · 요양원 + 주간보호 · 대화 모델 `gemini-3.8-live` · 음성은 중계 단일 경로.
- **판단 기준 셋**: ① 기존 ERP 가 하는 기능은 만들지 않는다 ② AI 산출물이 사람 확인 없이 공식 기록이
  되거나 보호자에게 가는 경로는 없다 — **테스트로 검증** ③ 제공 횟수·기록 품질·시간 절감을 측정할
  이벤트 로그를 1주차부터 남긴다.
- ⚠️ 전제: 공단이 "요양보호사 계획 + AI 진행 + 1인 병렬 감독"을 프로그램 제공으로 인정하는지는
  **기획 확인 사항**이다(파일럿 계획 §13). 결과에 따라 PF-19~PF-22 의 요구 수준이 바뀔 수 있다.

### 0-2. 사용자와 역할

| 역할 | `org_role` | 쓰는 곳 | 파일럿에서 하는 일 |
|---|---|---|---|
| 요양보호사 | `caregiver` | 앱(세션 진행) · 웹(연대기·일지·감독) | 세션 설계 확인 → 시작 → 감독, 일지 초안 확인 |
| 사회복지사 (신규) | `social_worker` | 웹 | 일지 확정·공개, 보호자 연결 승인 |
| 센터장 (신규) | `center_director` | 웹 | 권한 설정, 구성원 역할 지정 (현황판은 범위 밖) |
| 기관 관리자 | `org_admin` | 웹 | 기관을 만든 계정. 구성원 역할 지정·권한 설정 |
| 보호자 | `guardian` | 보호자 웹 | 공개된 "오늘의 이야기"·대화 관찰 리포트·공유 사진 열람 |
| 어르신 | (계정 없음) | 앱 어르신 표시 모드 | 대화만 한다. 기기를 조작하지 않는다 |

### 0-3. 기능 요구사항

#### 프로그램 일지 (기획 6-1·6-2 · D5·C2·C4·W1)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| PF-01 | 세션이 종료되면 서버가 **버튼 없이 자동으로** 프로그램 일지 초안 생성을 시작해야 한다. 트리거는 세션 종료 이벤트다 | Must |
| PF-02 | 일지 상태는 `생성 중 → 확인 대기 → 확정` 이고, 실패하면 `생성 실패`(재시도 가능)다. 공개·철회는 상태가 아니라 별도 공개 기록(`guardian_shares`)으로 관리한다 | Must |
| PF-03 | 자동 처리는 **확인 대기까지만** 간다. 확정은 권한 있는 사람만 할 수 있어야 하며, 서버 워커(서비스 계정)는 확정 상태를 **쓸 수 없어야** 한다(DB 가 집행) | Must |
| PF-04 | 일지는 공단 서식 필드를 가진다 — 프로그램 유형(기본 "인지활동 - 회상훈련") · 운영 일시(세션 시작·종료) · 장소(기관 기본 장소) · 진행자 · 참여자(1:1) · 목표(세션 설계) · 진행 내용 · 수급자 반응·특이사항 · **의견수렴**(신규) · 전반적 평가 · 다음 계획 · 사용 도구 | Must |
| PF-05 | **진행자는 세션을 시작·감독한 요양보호사**다. AI 를 진행자로 기록할 수 없어야 하고(확정 시 필수), AI 사용은 "사용 도구" 칸(기본 "AI 대화 프로그램 보조")에 따로 적는다 | Must |
| PF-06 | 분석 레코드(요약·관찰 지표·호응/저조 주제·추천 주제·소요 시간)를 일지 필드로 **자동 매핑**해야 한다. 초안의 모든 문장은 어르신 발화 근거(턴·원문 인용)를 가져야 한다 | Must |
| PF-07 | 초안에 진단성 표현(`인지 저하`·`우울`·`정서 불안`·`병원 진료 권장` 등)이 있으면 **그 필드만 비우고** 확인 대기로 넘겨야 한다(전체 실패가 아니다). 관찰한 사실만 적는다 — 예: "고향 이야기에서 발화가 많았고 웃음이 있었음" | Must |
| PF-08 | **확정 후 수정**은 사유 입력이 필수이고, 누가·언제·무엇을 바꿨는지 이력이 자동으로 남아야 한다(평가 대비 감사 추적) | Must |
| PF-09 | 초안이 마음에 들지 않으면 **다시 생성**할 수 있어야 한다(기존 수동 생성 기능의 유지) | Should |
| PF-10 | 일지 목록은 "확인 대기 N건"을 맨 위에 보여야 한다 | Must |
| PF-11 | 주간보호 어르신은 일지에 **제공 여부**와 **미제공 사유**(결석·컨디션 난조·거부·기타)를 남길 수 있어야 한다. 출석 관리 자체는 만들지 않는다(ERP 영역 — 기준 ①) | Should |
| PF-12 | 어르신 **장기요양등급**(1~5등급·인지지원등급)을 입력할 수 있어야 하며, 주간보호 기관에서는 필수다 | Should |
| PF-13 | 일지 사진 첨부는 유지한다(공유 사진 유형도 그대로) | Should |

#### 보호자 공개 (기획 6-5·6-6 · W3·W4)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| PF-14 | 보호자에게 공단 서식을 그대로 보여주지 않는다. 같은 일지 레코드에서 **보호자용 문장**을 따로 만들고, 이 문장도 사람이 승인해야 한다 | Must |
| PF-15 | 일지 공개는 **확정 + 보호자 문장 승인 + 공개 권한** 세 조건이 모두 충족될 때만 가능해야 한다(서버 강제) | Must |
| PF-16 | 보호자 소식 필터 "요양일지"를 **"오늘의 이야기"** 로 바꾼다. 열람 기록과 요양보호사 알림은 유지한다 | Must |
| PF-17 | 보호자 "분석" 메뉴를 **"대화 관찰 리포트"** 로 바꾸고 판정형 표현을 기술형으로 바꾼다(금지·허용 표: 파일럿 계획 §7). 모든 리포트 하단에 **"본 리포트는 대화 기록 요약이며 진단·평가 목적이 아닙니다."** 를 고정한다 | Must |
| PF-18 | 공개·철회 구조(F-26)는 그대로 둔다. 철회하면 보호자 화면에서 즉시 닫혀야 한다 | Must |

#### 감독·세션 운영 (기획 7-1·7-3·6-9 · D6·C3·C4·W2·M1~M6)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| PF-19 | 감독 화면에서 **기관 안의 진행 중 세션**을 볼 수 있어야 한다 — 어르신 이름·기기·경과 시간·현재 단계·상태(진행 중 / 침묵 지속 / 위기 발화(강조) / 종료 요청) | Must |
| PF-20 | 감독 화면에서 세션을 **원격으로 일시정지·재개·종료**할 수 있어야 하고, 다른 감독 화면에도 반영되어야 한다 | Must |
| PF-21 | 누가 언제 감독·개입했는지 기록이 남아야 한다("사람이 감독했다"는 증빙) | Must |
| PF-22 | 감독 화면은 **웹 우선**이며 요양보호사 휴대폰 브라우저에서 쓸 수 있어야 한다(반응형). 앱에는 만들지 않는다 | Must |
| PF-23 | 위기 발화·세션 이상 종료는 감독 화면을 보고 있지 않아도 요양보호사 휴대폰으로 **푸시**되어야 한다 | Must |
| PF-24 | 위기 발화는 감지 **즉시** 서버에 기록되어야 한다(세션 종료 시 일괄 기록으로는 실시간 알림이 불가능하다) | Must |
| PF-25 | 모바일 앱은 **요양보호사 모드**(어르신 선택·설계 확인·시작)와 **어르신 표시 모드**(큰 사진·자막·"말하는 중" 표시만, 조작 요소 없음)로 나뉜다 | Must |
| PF-26 | 어르신 표시 모드에는 위기 배너(전화번호)·전사 수정 패널·중계 컨트롤·확인 없이 끝내는 종료 버튼이 **없어야** 한다 — 신규 기능이기 전에 현 화면의 결함 수정이다 | Must |
| PF-27 | 어르신 표시 모드에서 요양보호사 모드로 돌아가려면 **숨김 제스처 또는 PIN** 이 필요하다 | Must |
| PF-28 | 원격 일시정지를 받으면 앱은 "잠시 쉬어요" 화면으로 바꾸고 마이크를 멈춘다 | Must |
| PF-29 | 기기 1대 = 동시에 세션 1개. 여러 기기가 각자 독립 세션을 돌린다 | Must(이미 충족 — 중계 `SESSION_BUSY`) |

#### 대화 정책 (기획 6-3 · 파일럿 계획 §9)

| ID | 요구사항 | 우선순위 |
|---|---|---|

| PF-31 | 목표 시간(세션 설계의 "예상 소요 시간", 없으면 기관 기본값)이 되면 마무리 단계로 넘어간다 | Must |
| PF-32 | 마무리 단계에서 소감 질문("오늘 이야기 어떠셨어요?")을 하고 그 답을 **의견수렴**으로 구조화해 저장한다 | Must |
| PF-33 | 주제 정책 — 설계된 주제 목록, 피할 주제(세션 설계 + 기관 기본), 반복 회피 | Must |
| PF-34 | 대화 스타일 — 짧은 문장, 한 번에 질문 하나, 응답이 짧거나 침묵하면 쉬운 질문(예·아니오·선택형), 재촉 금지 | Must |
| PF-35 | 종료 정책 — "그만할래", "힘들어" 같은 말에는 마무리 단계로 넘어가 짧게 끝내고 감독 화면에 알린다 | Should |
| PF-36 | 위기 대응 — 결정론 감지 시 **즉시 연결 종료(현재 동작 유지)** + 일시정지 시각 기록 + 위기 이벤트 즉시 기록 + 감독 화면·푸시 알림. AI 판단을 최종 근거로 삼지 않는다 | Must |

| PF-42 | 기관 전체 열람을 허용하는 대신 **누가 어느 어르신 기록을 열람했는지** 이벤트로 남긴다(최소 수집 원칙 보완) | Should |

#### 동의·계측·고령자 UI (기획 7-11·6-11 · W7·D8·M2)

## 3. 핵심 기능 요구사항

### 3-1. 연대기 입력 (M-01)

> 나는 요양보호사로서, 어르신의 생애 정보를 항목별로 입력하고 싶다. 왜냐하면 AI가 어르신의 실제 삶에 기반한 질문을 건네야 어르신이 편하게 반응하기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-01 | 시스템은 이름, 출생연도, 출신지, 직업 이력, 가족 구성, 주요 기억(최대 5개), 취미 항목을 입력받아야 한다 | Must |
| F-02 | 이름과 출생연도는 필수 항목이며, 비어 있을 경우 저장이 차단되고 안내 메시지가 표시되어야 한다 | Must |
| F-03 | 저장 완료 후 어르신 목록에 즉시 반영되어야 한다 | Must |
| F-04 | 기존 프로필을 수정할 때 저장된 내용이 그대로 불러와져야 한다 | Must |

### 3-2. LLM 회상 대화 생성 (M-02)

> 나는 경도 치매가 있는 어르신으로서, 내 고향과 젊은 시절 이야기를 주제로 AI가 먼저 말을 걸어주는 대화를 경험하고 싶다. 왜냐하면 누군가 내 삶을 알고 물어봐 줄 때 기억이 더 잘 떠오르기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-05 | 세션 시작 시 AI의 첫 질문에 어르신의 연대기 정보(출신지, 직업 등)가 반드시 포함되어야 한다 | Must |
| F-06 | AI는 동일한 주제를 연속으로 반복하지 않고, 고향 → 가족 → 직업 순으로 주제를 전환해야 한다 | ~~Must~~ 변경 → PF-30·PF-33 |
| F-07 | 어르신이 10초 이상 침묵하거나 짧게 답할 경우, AI는 더 쉬운 힌트를 제공하거나 주제를 전환해야 한다 | ~~Must~~ 변경 → PF-34 |
| F-08 | AI는 사별, 전쟁 등 고통스러운 기억이 언급될 경우 자연스럽게 다른 주제로 전환해야 한다 | ~~Should~~ 변경 → PF-33·PF-36 |
| F-09 | 하나의 세션은 3~5턴, 약 10분을 기본 설계로 한다 | ~~Should~~ 변경 → PF-31 |
| F-10 | LLM 응답은 JSON 형식(`question`, `topic`, `switch_topic`)으로 반환되어야 한다 | ~~Must~~ 폐기 §0-6 |

### 3-3. TTS 음성 출력 (M-03)

> 나는 스마트폰 사용이 익숙하지 않은 어르신으로서, 화면을 보지 않아도 AI의 질문을 귀로 들을 수 있으면 좋겠다. 왜냐하면 화면 조작이 부담스럽고, 말로 대화하는 것이 훨씬 편하기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-11 | AI 질문은 세션 화면 진입 시 자동으로 음성 재생되어야 한다 (별도 버튼 조작 불필요) | Must |
| F-12 | 음성 재생 속도는 일반 대화보다 느리게 설정되어야 한다 | Must |
| F-13 | 음성 재생이 완료되면 마이크가 자동으로 활성화되어야 한다 | Should |
| F-14 | LLM 스트리밍 응답을 문장 단위로 분할하여 TTS를 순차 재생해야 한다 (체감 대기 최소화) | Should |

### 3-4. STT 음성 입력 (M-04)

> 나는 경도 치매가 있는 어르신으로서, 그냥 말로 대답하면 AI가 알아듣고 다음 대화를 이어가 주면 좋겠다. 왜냐하면 타이핑이 어렵고, 말하는 것이 가장 자연스러운 나의 소통 방식이기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-15 | 어르신의 발화가 끝난 후 3초 이내에 텍스트로 변환되어 화면에 표시되어야 한다 | Must |
| F-16 | 변환된 텍스트를 바탕으로 LLM이 다음 질문을 자동으로 생성하고 음성으로 재생해야 한다 | Must · 서술 변경 §0-6 |
| F-17 | 요양보호사는 STT 오인식 텍스트를 수동으로 수정할 수 있어야 하며, 수정된 내용 기준으로 LLM이 응답해야 한다 | ~~Should~~ 폐기 §0-6 |

### 3-5. 세션 로그 저장 (S-01)

## 9. 성공 기준

| 항목 | 기준 |

| STT 응답 속도 | 발화 종료 후 3초 이내 텍스트 표시 |
| TTS 체감 지연 | LLM 응답 시작 후 2초 이내 첫 음성 재생 |
