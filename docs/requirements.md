## 3. 핵심 기능 요구사항

### 3-1. 연대기 입력 (M-01)

> 나는 요양보호사로서, 어르신의 생애 정보를 항목별로 입력하고 싶다. 왜냐하면 AI가 어르신의 실제 삶에 기반한 질문을 건네야 어르신이 편하게 반응하기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-01 | 시스템은 이름, 출생연도, 출신지, 직업 이력, 가족 구성, 주요 기억(최대 5개), 취미 항목을 입력받아야 한다 | Must |
| F-02 | 이름과 출생연도는 필수 항목이며, 비어 있을 경우 저장이 차단되고 안내 메시지가 표시되어야 한다 | Must |
| F-03 | 저장 완료 후 어르신 목록에 즉시 반영되어야 한다 | Must |
| F-04 | 기존 프로필을 수정할 때 저장된 내용이 그대로 불러와져야 한다 | Must |

### 3-2. LLM 회상 대화 생성 (M-02)

> 나는 경도 치매가 있는 어르신으로서, 내 고향과 젊은 시절 이야기를 주제로 AI가 먼저 말을 걸어주는 대화를 경험하고 싶다. 왜냐하면 누군가 내 삶을 알고 물어봐 줄 때 기억이 더 잘 떠오르기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-05 | 세션 시작 시 AI의 첫 질문에 어르신의 연대기 정보(출신지, 직업 등)가 반드시 포함되어야 한다 | Must |
| F-06 | AI는 동일한 주제를 연속으로 반복하지 않고, 고향 → 가족 → 직업 순으로 주제를 전환해야 한다 | Must |
| F-07 | 어르신이 10초 이상 침묵하거나 짧게 답할 경우, AI는 더 쉬운 힌트를 제공하거나 주제를 전환해야 한다 | Must |
| F-08 | AI는 사별, 전쟁 등 고통스러운 기억이 언급될 경우 자연스럽게 다른 주제로 전환해야 한다 | Should |
| F-09 | 하나의 세션은 3~5턴, 약 10분을 기본 설계로 한다 | Should |
| F-10 | LLM 응답은 JSON 형식(`question`, `topic`, `switch_topic`)으로 반환되어야 한다 | Must |

### 3-3. TTS 음성 출력 (M-03)

> 나는 스마트폰 사용이 익숙하지 않은 어르신으로서, 화면을 보지 않아도 AI의 질문을 귀로 들을 수 있으면 좋겠다. 왜냐하면 화면 조작이 부담스럽고, 말로 대화하는 것이 훨씬 편하기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-11 | AI 질문은 세션 화면 진입 시 자동으로 음성 재생되어야 한다 (별도 버튼 조작 불필요) | Must |
| F-12 | 음성 재생 속도는 일반 대화보다 느리게 설정되어야 한다 | Must |
| F-13 | 음성 재생이 완료되면 마이크가 자동으로 활성화되어야 한다 | Should |
| F-14 | LLM 스트리밍 응답을 문장 단위로 분할하여 TTS를 순차 재생해야 한다 (체감 대기 최소화) | Should |

### 3-4. STT 음성 입력 (M-04)

> 나는 경도 치매가 있는 어르신으로서, 그냥 말로 대답하면 AI가 알아듣고 다음 대화를 이어가 주면 좋겠다. 왜냐하면 타이핑이 어렵고, 말하는 것이 가장 자연스러운 나의 소통 방식이기 때문이다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-15 | 어르신의 발화가 끝난 후 3초 이내에 텍스트로 변환되어 화면에 표시되어야 한다 | Must |
| F-16 | 변환된 텍스트를 바탕으로 LLM이 다음 질문을 자동으로 생성하고 음성으로 재생해야 한다 | Must |
| F-17 | 요양보호사는 STT 오인식 텍스트를 수동으로 수정할 수 있어야 하며, 수정된 내용 기준으로 LLM이 응답해야 한다 | Should |

### 3-5. 세션 로그 저장 (S-01)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-18 | 세션 종료 시 대화 전문(발화자, 텍스트, 발화 시각)이 자동으로 저장되어야 한다 | Should |
| F-19 | 요양보호사는 종료된 세션의 대화 전문과 총 턴 수를 조회할 수 있어야 한다 | Should |
| F-20 | 요양보호사는 어르신별 세션 이력을 날짜 내림차순으로 조회할 수 있어야 한다 | Should |

### 3-6. 세션 핸드오프·종료 (모바일)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-21 | 모바일 앱은 요양보호사 로그인 상태에서 어르신을 선택해 세션을 시작하고, "어르신께 기기를 전달해 주세요" 안내 화면을 거쳐야 한다 | Must |
| F-22 | 세션은 설계 턴 수 도달 또는 침묵 타임아웃 시 자동으로 종료되어야 한다(요양보호사가 기기를 들고 있지 않아도) | Must |
| F-23 | 어르신은 별도 로그인 없이 진입하되, 데이터 접근은 기기에 저장된 요양보호사 세션으로 인가되어야 한다 | Must |

### 3-7. 웹 1차 MVP — 현직자 인터뷰 반영 (2026-07-13, PLAN §2′ Phase W)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-24 | 요양보호사는 요양일지를 **사진 촬영 업로드·직접 타이핑·구어(음성) 입력** 3가지 경로로 작성할 수 있어야 한다 | Must |
| F-25 | AI가 입력 원문(사진 인식/음성 전사 포함)으로 일지 초안을 작성하되, **요양보호사 확인 후에만 저장**되어야 한다 | Must |
| F-26 | 요양보호사는 오늘 공개할 데이터(일지·분석·요약)를 **체크리스트로 선택해 공개**하고, 공개 이력을 **철회**할 수 있어야 한다(감사 기록 포함) | Must |
| F-27 | 앱에서 대화가 종료되면 분석 결과가 **실시간(Realtime)** 으로 요양보호사 웹 분석 페이지·대시보드에 반영되어야 한다 | Must |
| F-28 | 보호자는 **소셜 로그인(실계정)** 후에만 접근 가능하며, **어르신 영속 코드로 연결 요청 + 요양보호사 승인**을 거친 어르신 데이터만 볼 수 있어야 한다 | Must |
| F-29 | 보호자에게는 **공개(커밋)된 데이터만** 노출되어야 한다(서버 RLS로 강제 — 클라이언트 필터 금지) | Must |
| F-30 | 초기화면은 서비스 소개+**소셜 로그인**이며, 로그인 시 **역할에 따라 자동으로**(미가입자는 회원가입 온보딩으로) 요양보호사/보호자 페이지로 이동해야 한다 | Must |
| F-31 | AI 에이전트가 요양보호사(일지 초안·공개 대행·요약)와 보호자(기록·분석 설명)를 보조하되, **도구 실행 전 사람 확인**을 거쳐야 한다 | Should |
| F-32 | 로그인·회원가입 수단은 **이메일(아이디)+비밀번호** 및 **소셜 로그인 3종(구글·카카오·네이버)** 을 **병행** 제공한다(2026-07-23 이메일 재도입 — 구 "이메일 미제공" 철회). 구글·카카오=Supabase 네이티브, 네이버=커스텀 Edge Function 연동 | Must |
| F-37 | 이메일 로그인 사용자를 위해 **아이디(이메일) 찾기**(이름+전화 → 마스킹 이메일)·**비밀번호 찾기/재설정**(메일 링크)·**이메일 회원가입**을 제공해야 한다 | Must |
| F-38 | 소셜 로그인으로 회원가입 시 provider의 **본인인증 정보(이름·전화 등)** 를 동의 범위에서 가져와 온보딩 기본정보에 프리필해야 한다(구글은 전화 미제공) | Should |
| F-33 | 회원가입은 **소셜 로그인 후 기본정보 입력(온보딩)** 방식이어야 한다 — 이름·전화번호·역할(요양보호사/보호자). 요양보호사=기관명(새 기관) 또는 **어르신 코드(기존 기관 합류·승인 대기)**, 보호자=어르신 코드(선택). 개인정보·소셜 제3자 동의 포함. 온보딩 완료 전에는 데이터 화면에 접근할 수 없어야 한다 | Must |
| F-34 | 보호자는 **로그인 후에도** 어르신 영속 코드 입력으로 어르신을 자기 계정에 연결할 수 있어야 한다(가입 시 연결과 동일 메커니즘·요양보호사 최종 승인) | Must |
| F-35 | 어르신은 **영속 코드**를 가지며, 담당 요양보호사가 **변경되거나 추가**될 때 그 코드로 배정받아 **기존 기록(연대기·세션·분석·일지)을 그대로 인계**받아야 한다(신규 어르신 생성 없이). 같은 기관 안에서만 배정 가능 | Must |
| F-36 | 신규 요양보호사는 **어르신 코드로 기존 기관에 합류**할 수 있어야 하며(온보딩), 합류는 **승인형**이어야 한다 — 코드로 합류 요청(pending) → 기관 관리자 또는 그 어르신의 활성 담당이 승인해야 데이터 접근이 열린다. 코드 소지만으로 즉시 권한을 얻어선 안 된다(자가승인 불가) | Must |
| NF-W3 | 어르신 데이터 접근은 **배정된(active) 요양보호사 또는 기관 관리자**로 제한되어야 하며(어르신 단위 최소권한), 어르신 코드는 보호자에게 노출되지 않아야 한다(권한 상승 차단). 미승인(pending) 요양보호사는 데이터에 접근할 수 없어야 하고, 요양보호사 계정 삭제 시에도 어르신 데이터는 보존되어야 한다. 어르신 코드 회전(rotate)은 서버에서 생성되어 예측·재사용이 불가능해야 한다 | Must |
| NF-W1 | `safety_events` 등 민감 데이터의 RLS는 **guardian 역할을 배제**해야 하며, 보호자 데이터 경로는 `guardian_shares` 경유로만 열린다 | Must |
| NF-W2 | 이메일 계정 비밀번호는 **Supabase Auth가 해싱·관리**(평문 미저장)하고, 소셜은 위임 인증이며 프로필은 **최소 수집**(이메일·이름·동의한 전화). 네이버 client secret·SMTP 자격증명 등 비밀값은 **서버(Edge Function/secrets)** 에만 보관한다 | Must |

## 9. 성공 기준

### 기능 완성 기준

| 항목 | 기준 |
|---|---|
| 파이프라인 완성 | 연대기 입력 → LLM 생성 → TTS 출력 → STT 입력 → 로그 저장까지 오류 없이 동작 |
| 개인화 검증 | AI 첫 질문에 어르신의 연대기 정보(출신지·직업 중 1개 이상)가 포함됨 |
| 주제 전환 | 동일 주제 3회 연속 반복 없이 자연스럽게 전환됨 |
| STT 응답 속도 | 발화 종료 후 3초 이내 텍스트 표시 |
| TTS 체감 지연 | LLM 응답 시작 후 2초 이내 첫 음성 재생 |

### 파일럿 성공 기준

| 항목 | 기준 |
|---|---|
| 세션 시작 속도 | 요양보호사가 연대기 입력 후 5분 이내에 세션 시작 가능 |
| 대화 지속성 | 어르신이 3턴 이상 대화 지속 |
| 기록 자동화 | 세션 로그가 자동 저장되어 수기 기록 불필요 |
| 요양보호사 만족도 | 파일럿 후 설문에서 5점 만점 기준 평균 4점 이상 |
| 시스템 안정성 | 파일럿 세션 중 치명적 오류(앱 강제 종료, 대화 단절) 발생 0회 |

### 발표 시연 기준

| 항목 | 내용 |
|---|---|

| 차별점 장면 | AI 질문에 어르신의 실제 연대기 정보(고향·직업)가 반영된 개인화 대화 |
| 백업 시나리오 | 네트워크 불안정 대비 녹화 영상 준비 |
