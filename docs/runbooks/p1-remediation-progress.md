## R005 — Live 토큰 발급 권한·사용 한도

코드 수정 및 운영 반영 완료(2026-09-09). `20260909010000_live_token_authorization.sql`과 live-token 운영 버전 5에 반영했다.

- 입력은 session_id 한 개로 제한한다. 로그인 검증 후 DB가 온보딩, caregiver/org_admin 역할, 기관 일치, 활성 배정(기관 관리자는 기관 범위), active 세션 및 필수 동의 3종의 현행 v1.0·미철회를 검사한다.
- 클라이언트가 role/user_id/profile_id를 바꿔 보내 권한 판정을 바꿀 수 없다. DB RPC는 auth.uid()를 사용하며 anon은 실행할 수 없다.
- 앱은 서버 세션 ID가 생성된 뒤 토큰을 요청한다. DB 생성 실패로 ID가 없는 경우 유료 Live 연결을 시도하지 않는다. 이미 배포된 구버전 앱의 빈 본문 요청도 거부되므로 앱 수정본 배포가 필요하다.
- 사용자 분당 3회·서울 기준 일 20회, 기관 일 200회, 프로젝트 일 2,000회의 고정 시간 구간 한도를 적용했다. 설정 테이블은 일반 사용자에게 비공개다. 실패한 공급자 요청도 예약 횟수를 돌려주지 않아 반복 실패를 이용한 우회를 막는다.
- DB의 조건부 UPSERT로 한도를 증가시키고 어느 한도라도 초과하면 해당 호출의 모든 증가를 롤백한다. 분/일 경계에서 각각의 새 구간 한도가 적용된다. 카운터는 개인정보 본문을 포함하지 않으며 2일 초과분을 정리한다.
- 이 한도는 **발급 횟수 상한**이다. 이미 발급한 토큰/열린 연결을 강제로 취소하거나 실제 원화·달러 사용액을 제한하지 않는다. 공급자 과금 상한·계약 및 진행 중 동의 철회 처리는 R050/R010 후속 범위로 남는다.
- 본문 1KB 제한, 잘못된 입력 400, 자격/동의 부족 403, 한도 초과 429, DB 확인 실패 503, no-store 응답을 적용했다.

검증: 전체 격리 DB 회귀 통과(보호자·배정 해지·다른 기관·종료/예정 세션·철회/구버전/누락 동의 거절, 네 종류 한도 초과 및 부분 증가 롤백), Edge 테스트 15개, 모바일 엔진 토큰 테스트 3개, 모노레포 타입 검사·린트 통과. 실제 여러 PostgreSQL 연결의 부하 시험과 인증된 실기기 E2E는 별도다.

운영: Supabase CLI `db query --linked --file`로 이 마이그레이션만 적용하고 같은 트랜잭션에 버전 이력을 기록했다. 이전 SQL Editor 적용분은 재실행하지 않았다. CLI로 live-token 단일 함수를 배포했으며 ACTIVE v5, verify_jwt=true와 운영 한도·RPC 권한·마이그레이션 이력을 확인했다. 운영 소스를 다시 내려받아 저장소 파일과 일치 여부를 검증한다. `.env` 등 민감 파일은 읽지 않는다.

R005 커밋: `1c7171a` — origin/main 푸시 완료.

## R006 — 모바일 Google/Kakao PKCE 코드 교환

코드 수정·자동 검증 완료. exchangeCodeForSession에 callback URL 전체를 넘기던 호출을 URL에서 추출한 code 전달로 수정했다. 같은 공급자의 중복 호출은 진행 중 Promise를 재사용하고 다른 공급자의 동시 로그인은 거절하여 PKCE verifier가 덮어써지는 것을 막는다. 완료·오류·취소 후에는 재시도할 수 있다.

콜백 프로토콜/호스트/경로를 요청한 redirectTo와 대조하고, OAuth 오류는 고정 안내로 전달한다. 취소와 콜백 실패를 구분한다. 기존 암시적 콜백의 두 토큰을 이용한 세션 설정은 유지했다. 네이버 서버 state 흐름은 R007에서 별도로 수정한다.

검증: Google/Kakao 각각 code 전달, 취소/dismiss, 오류·잘못된 경로, 중복/교차 공급자 호출, 교환 실패 후 재시도, 기존 암시적 콜백을 다루는 12개 테스트와 모바일 타입 검사·린트 통과. 실제 독립 앱에서 두 공급자 신규/기존 계정 로그인·userRow·라우팅 확인은 사용자 요청에 따라 후속 실기기 검증으로 남긴다. 모바일 코드 변경이며 이번 항목에 Supabase 함수 배포는 필요 없다.

계약 근거: [Supabase exchangeCodeForSession](https://supabase.com/docs/reference/javascript/auth-exchangecodeforsession).

R006 커밋: `0809f0c` — origin/main 푸시 및 CI 통과.

## R007 — 네이버 모바일 일회성 인증 요청

코드 수정·격리 검증·운영 배포 완료. 실제 네이버 계정 로그인은 후속 실기기/외부 설정 검증 항목이다.

- 앱은 Expo AuthRequest의 암호학적 verifier/S256 challenge를 생성한다. challenge를 서버 authorize에 보내고 verifier는 앱 메모리에만 둔다. Google/Kakao/Naver의 동시 요청은 하나로 제한한다.
- 서버는 challenge·앱 요청 상태·허용된 콜백·만료 시각을 서명하고 HttpOnly nonce 쿠키로 시작 브라우저를 확인한다. 네이버 인가 코드는 HTTPS 서버 콜백으로만 받는다.
- 딥링크에는 일회성 transaction_id와 요청 상태만 반환한다. 앱이 verifier로 교환할 때 서버에서 S256을 계산하고 DB가 원자적으로 한 번만 소비한다. 구형 POST {code,state} 경로는 닫았다. 구버전 앱은 수정본 업데이트가 필요하다.
- 저장/소비 RPC는 service_role 전용이고 anon/authenticated는 실행할 수 없다. 사용 후 인가 코드·state를 비우되 만료까지 재사용 차단 행을 유지한다. 만료된 행은 다음 저장 요청에서 정리하며, 동시 저장을 직렬화하고 최대 10,000행으로 제한한다. 이는 IP별 남용 방어 전체를 대체하지 않는다(R052 후속).
- 서버 서명키는 비밀 서비스 키에서만 파생하고 anon 키 폴백을 제거했다. 요청 본문 1KB 제한, no-store 응답, 변조/만료 state 및 잘못된 쿠키의 안전한 거절을 추가했다.
- 운영 검증에서 발견한 Supabase 내부 URL 재작성 문제도 수정했다. req.url의 내부 http 경로 대신 SUPABASE_URL을 기준으로 공개 HTTPS 콜백을 생성한다.

검증: Edge 11개(서명 변조, 쿠키/만료, 다른 verifier, 재사용, 기존 직접 POST 거절, 웹 흐름 유지, 내부 URL 재작성 포함), 모바일 소셜 16개(기존 R006 12개+네이버 4개), 전체 SQL 회귀, 타입 검사·린트 통과. SQL은 잘못된 challenge·만료·재사용·사용 후 코드 파기 및 RPC ACL을 검사한다. 테스트에서 공급자/API 값은 합성 값만 사용했다.

운영: CLI로 `20260909020000_naver_mobile_handoff`와 이력을 같은 트랜잭션에 적용했고 naver-auth만 ACTIVE v4로 배포했다. 로그인 전 함수의 기존 verify_jwt=false를 유지했다. RPC 권한, 마이그레이션 이력, 배포 소스 일치, 빈 POST 400/no-store 및 authorize 302를 확인했다. live-token(v5)/stt-transcribe(v1)는 변경하지 않았다. 배포 전 소스는 `%TEMP%/memoryon-r007-20260909/before`에 보관했다.

후속 검증: 네이버 개발자센터 Callback URL에 `https://ufkbzpdjomtmxjipmwub.supabase.co/functions/v1/naver-auth/callback`이 등록되어야 한다. 이번에는 네이버 개발자센터 설정이나 시크릿을 열지 않았으며 실제 등록 여부는 확인되지 않았다. 앱 반환 주소는 기본 `giokon://auth/callback`만 허용하며, 개발 빌드의 다른 주소가 필요하면 서버 MOBILE_AUTH_REDIRECTS의 정확한 허용 목록으로 관리한다. 실제 공급자 로그인·취소·독립 앱 복귀 검증은 사용자 요청에 따라 후속으로 남긴다.

R007 커밋: `d5f9974` — origin/main 푸시 및 CI 통과.

## R008 — 앱 전체 라우트·실행 중 권한 변경

코드 수정·자동 검증·DB 운영 반영 완료. 모바일 수정본 설치와 실기기 시나리오 검증은 후속이다.

- 루트 Stack.Protected가 로그인·스플래시를 제외한 17개 화면을 보호한다. 미로그인·조회 중·보호자·미온보딩 계정의 직접 링크 진입도 차단한다. 새 화면이 보호 목록에서 빠지면 파일 목록 대조 테스트가 실패한다.
- users 변경 구독, 배정 변경 이벤트, 앱 복귀, 포그라운드 30초 주기 검사로 서버 계정 정보를 다시 확인한다. 사용자 본인의 활성 배정 ID는 페이지별로 모두 읽고, 진행 중 어르신은 profiles RLS 조회로 접근 가능 여부를 확인한다. 추가 배정만으로 정상 대화를 끊지는 않는다.
- 역할·기관 변경, 배정 소실, 진행 중 어르신 접근 불가 시 Live 연결·기본 TTS·진행/종료 세션 메모리·Query 캐시를 정리하고 내비게이터를 새로 만든다. 실패하거나 10초를 넘긴 계정 검사는 기존 허용 값을 유지하지 않고 접근을 차단한다. 이전 계정/이전 요청의 늦은 응답은 반영하지 않는다.
- Live 토큰 요청·WebSocket 연결 도중 권한이 철회되어도 늦게 연결이 살아나지 않도록 연결 중 엔진도 취소한다. 소켓은 네이티브 재생 정리 완료를 기다리지 않고 먼저 닫는다.
- users 실시간 발행만 추가하는 `20260909030000_users_access_realtime`을 Supabase CLI로 적용하고 같은 트랜잭션에 이력을 기록했다. 운영 users 발행·RLS 유지·이력 등록 모두 확인했다. Edge Function 변경은 없다.

검증: 모바일 테스트 전체 71개(직접 라우트 보호·늦은 응답·권한 소실·타임아웃·배정 페이지 처리·연결 중 취소 포함), 전체 SQL 회귀, 모노레포 타입 검사·린트 및 Android Metro 번들 생성 통과. 번들은 EXPO_NO_DOTENV=1로 민감 파일을 읽지 않고 임시 폴더에 생성했다. 실제 독립 앱의 딥링크·기관 변경·배정 해지·백그라운드 복귀 동작은 사용자 요청에 따라 실기기 후속 검증으로 남긴다.

범위: 이는 정상 앱의 접근 경계이며 서버의 RLS/토큰 권한 검사를 대체하지 않는다. 실시간 이벤트가 누락되면 주기 검사와 조회 제한 시간만큼 반영이 지연될 수 있다. 동의 철회의 진행 중 세션 차단은 R010, 로그아웃의 저장소·지연 쓰기까지 포함한 완전한 계정 격리는 R009, 강제 종료 후 DB 세션 상태·미저장 기록 복구는 후속 세션 항목에서 별도로 점검한다.

구현 근거: [Expo Router protected routes](https://docs.expo.dev/router/advanced/protected/).
