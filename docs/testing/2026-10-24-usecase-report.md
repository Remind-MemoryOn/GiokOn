# 유스케이스 테스트 결과 — 2026-10-24

> **수정 전 시험 기록이다.** ✅ 2026-10-24 후속 BB-01 코드 수정·로컬 재실행에서 웹 6/6 통과했다. [수정·재검증](2026-10-24-bb01-fix.md). 아래 원래 실패 판정·증거는 보존한다.

**선정한 로컬 유스케이스 실행 완료. 전체 제품 합격은 보류한다.** 웹 6개 중 5개 통과·1개 실패, DB 4개 모두 통과. 실패는 기존 BB-01(로그인 후 감독 화면 복귀)과 같다. 실제 앱·외부 연동 4개 유스케이스는 대기다. 제품 코드 수정과 화이트박스 커버리지 검증은 수행하지 않았다.

## 1. 시험 방식과 증거

- 기준: [파일럿 요구사항](../requirements.md), [개발 계획](../plans/pilot-development-plan.md), [앞선 블랙박스 결과](2026-10-24-blackbox-report.md). 대상 커밋은 `ee1d3de6dfc3c457e71f48b69fc62285f719ced1`이며 제품 소스는 앞선 시험과 같다.
- 웹: 실제 제품 빌드·AuthProvider·라우터·화면을 사용한다. 역할마다 독립 브라우저 컨텍스트에서 로그인하며, 공유된 합성 HTTP 서버 상태로 역할 간 저장 결과를 이어 받는다. 감사용 인증 교체·Query 캐시 주입은 사용하지 않았다.
- 웹의 HTTP 인증·저장·승인·이력 응답은 시험용 모형이다. 화면이 보내는 요청과 표시·재조회 결과를 검증하며, 이 시험만으로 실제 서버 권한이나 영속성을 증명하지 않는다.
- DB: 새 PostgreSQL 16에 마이그레이션 84개 적용 → 합성 인물·기관 생성 → 공개 RPC/테이블 요청 → 실제 저장 결과 확인. `authenticated`의 `app` 스키마 USAGE를 회수해 운영과 같은 조건으로 실행했다. Auth·외부 확장은 기존 테스트 심을 사용한다.
- 웹 시험과 DB 시험은 분리되어 있다. 동일 브라우저 요청을 실제 DB까지 연결한 전체 종단 시험은 대기다. 같은 업무가 두 층에 포함되므로 10개를 서로 다른 사용자 목표 10개로 해석하지 않는다.
- 환경: Windows, Node v24.16.0, pnpm 10.33.0, Microsoft Edge headless Playwright. `.env` 등 민감 파일 조회·운영 DB 쓰기·배포 없음. DB 컨테이너는 `--network none`으로 만들고 러너가 시험 후 삭제한다.

## 2. 웹 유스케이스 명세와 결과

### UC-W01 · 일지 작성부터 보호자 열람·철회까지 — PASS

- **목표·액터**: 요양보호사가 기록을 작성하고, 담당 사회복지사가 확인·확정·공개하며, 승인 연결된 보호자가 열람한다. 관련 요구 PF-03~05·PF-14~16·PF-18.
- **사전조건**: 기관 합류 완료, 어르신 등록, 요양보호사·사회복지사 담당 배정, 보호자 연결 승인. 새 수기 일지를 쓰는 흐름이다.
- **트리거**: 요양보호사가 새 프로그램 일지를 연다.
- **정상 흐름**: ① 진행자를 선택하고 공단 내용·보호자 문장을 작성·승인 후 임시 저장 → ② 다른 컨텍스트의 사회복지사가 같은 일지의 내용을 확인하고 확정 → ③ 보호자 대상으로 공개 → ④ 보호자가 승인 문장을 열람 → ⑤ 사회복지사가 공개를 철회하고 보호자가 다시 조회한다.
- **예상 사후조건**: 일지 1건이 확인 대기→확정으로 이어진다. 보호자에게 공단 내부 문장은 표시되지 않는다. 열람 RPC가 호출되고, 철회 후 새 조회에서는 승인 문장도 사라진다.
- **실제**: 5단계 모두 통과. 브라우저를 새로 조회한 결과이며, 열어 둔 다른 기기의 2초 내 실시간 철회 반영을 검증한 것은 아니다. 실제 서버 공개·열람·철회는 UC-D02에서 별도 검증했다.

### UC-W02 · 직원 초대·코드 오류 복구·합류 승인 — PASS

- **목표·액터**: 기관 관리자가 초대하고 신입 직원이 승인을 거쳐 기관 기록에 접근한다. PF-47.
- **사전조건**: 관리자는 기관 소속, 신입은 가입 완료·기관 미소속이며 기존 합류 요청이 없다.
- **트리거**: 관리자가 ‘코드 만들기’를 누른다.
- **정상 흐름**: ① 초대 코드 발급 → ② 신입이 보호된 기록 주소에 접근하면 합류 화면으로 이동 → ③ 유효 코드로 합류 요청 → ④ 관리자가 확인창에서 승인 → ⑤ 신입이 ‘승인 확인’ 후 어르신 목록에 진입한다.
- **대안·예외**: 잘못된 코드를 먼저 입력했다. 오류 안내가 보이고 요청은 만들어지지 않았다. 유효 코드로 수정하면 이어서 요청할 수 있었다.
- **예상 사후조건·실제**: 승인 전에는 신입 화면에서 어르신 조회를 보내지 않고 기관 소속도 비어 있다. 승인 후 같은 기관의 어르신이 보인다. 모두 통과. 실제 서버의 승인 전 0건·교대 열람·타 기관 격리는 UC-D01에서 확인했다.

### UC-W03 · 감독자가 일시정지·재개·종료 요청 — PASS

- **목표·액터**: 요양보호사가 진행 중 세션을 감독·조작한다. PF-19~22.
- **사전조건**: 기관의 진행 중 세션 1건, 로그인한 요양보호사.
- **트리거**: 감독 화면에서 ‘일시정지’를 누른다.
- **정상 흐름**: 정지 확인 → ‘재개’ 표시 및 재개 조작 → 종료 확인 → 종료 RPC 전송.
- **대안·예외**: 첫 종료 확인에서는 ‘취소’를 눌렀다. 종료 요청이 전송되지 않았다. 다시 종료를 확인하면 전송됐다.
- **예상 사후조건·실제**: 같은 세션 ID로 `pause → resume → end` 순서의 요청이 1회씩 전송됐다. 통과. 실제 앱의 마이크 정지·재개·저장은 UC-P01의 대기 범위다. 실제 DB의 제어 요청과 중계용 `session_tick` 판정은 UC-D02에서 확인했다.

### UC-W04 · 안전 알림의 감독 링크에서 로그인 후 복귀 — FAIL (BB-01)

- **목표·액터**: 로그아웃된 요양보호사가 감독 링크를 열어 로그인한 뒤 즉시 감독한다. PF-22·PF-23 연결 흐름.
- **사전조건·트리거**: 로그아웃 상태에서 `/caregiver/supervision`을 연다. 푸시 전달은 포함하지 않고 푸시가 여는 URL 이후부터 시험했다.
- **정상 흐름**: 로그인으로 이동 → 유효한 시험 계정으로 로그인 → 원래 감독 화면에 복귀.
- **예상 사후조건**: 주소 `/caregiver/supervision`, 감독 화면 표시.
- **실제**: 로그인은 성공하지만 **`/caregiver` 대시보드**로 이동한다. 재현 절차와 화면은 위 증거에 있다. 앞선 블랙박스 BB-01과 동일하므로 새 결함으로 중복 집계하지 않는다. P2, 미수정.

### UC-W05 · 종료된 대화의 안전 알림 확인 — PASS

- **목표·액터**: 요양보호사가 세션이 끝난 뒤에도 남은 안전 알림을 보고 확인 처리한다. PF-19·PF-24의 감독 후속.
- **사전조건**: 진행 중 세션 없음, 어르신의 미확인 안전 이벤트 1건. 감지·중계 생성은 시험 데이터로 준비했다.
- **트리거·흐름**: 감독 화면 진입 → 발췌·확인 버튼 관찰 → ‘확인했어요’ → 다시 조회.
- **예상 사후조건·실제**: 확인 PATCH와 확인 시각이 남고 미확인 목록에서 제거되며 재조회에서도 유지된다. 통과. 실제 위험 감지·현장 대응·푸시 수신 성공을 뜻하지 않는다.

### UC-W06 · 확정 기록의 사유 있는 정정·이력 열람 — PASS

- **목표·액터**: 확정 권한이 있는 사회복지사가 오기를 고치고 변경 이력을 확인한다. PF-08.
- **사전조건·트리거**: 확정 일지의 장소가 잘못되어 정정한다.
- **정상 흐름**: 장소 수정 → 사유 작성 → 변경 저장 → 다시 열어 장소 확인 → ‘수정 이력’ 탭에서 사유 확인.
- **대안·예외**: 사유를 비운 첫 저장은 안내와 함께 차단됐고 PATCH 0건이었다.
- **예상 사후조건·실제**: 사유 입력 후 장소가 유지되고 확정 상태도 유지되며 이력 1건을 열람한다. 통과. 이력 생성은 웹 모형 응답이고, 실제 DB의 이력·삭제 보호는 UC-D03에서 확인했다.

선정한 핵심 유스케이스에 대한 결과다. 모든 역할·시설 유형·권한 위임 변경·동시 기기 수·생성 내용 품질을 전수 검증한 것은 아니다. 배포본과 현재 로컬 커밋의 동일성도 이번 시험에서 확인하지 않았다. 문장/분기/경로 커버리지·변이 테스트 및 신규 CI 게이트 등록은 화이트박스 단계와 별도로 남겼다.

시험 준비 중에는 화면의 확인창·탭 역할과 비동기 조회 완료 시점을 테스트가 올바르게 기다리도록 고쳤고, 합성 응답이 요청의 승인 증거를 보존하도록 보정했다. 제품 코드는 바꾸지 않았다. 위 최종 로그를 기준으로 집계하며 초기 테스트 준비 오류는 제품 결함으로 세지 않는다.
