## 1. 기획의 목적

현재의 등록 표현 검색을 넘어, 어르신이 같은 의미를 서로 다른 방식으로 말하는 상황과 개인별 표현을 포괄한다. 발화 내용뿐 아니라 속도·톤·침묵 등의 음성 특징을 함께 보고 대화의 부담과 감정 표현을 해석한다.

목적은 다음 네 가지다.

1. 등록 어구에 없는 위험·고통·거부 표현을 더 넓게 다룬다.
2. 주체·시점·부정·인용·직전 대화를 고려해 해석한다.
3. 어르신 반응에 맞춰 질문 길이, 기다림, 공감, 전환·휴식 제안을 조절한다.
4. 상황·판단·대응·이후 반응을 연결해 향후 Qwen 대화 특화 모델의 학습 기반을 만든다.

본 기획의 위험 감지는 직원 확인이 필요한 신호의 탐지다. 의료적 위험 진단, 우울증·치매 단계 판정, 실제 내면 감정의 확정을 목표로 하지 않는다.

## 4. 변경하지 않는 기존 제약

1. 명확한 위기 신호의 기존 즉시 종료 경로를 임의로 일시정지로 낮추지 않는다.
2. 현재 규칙에서 급성 고통으로 처리해 중단하는 경로도 문서만으로 완화하지 않는다.
3. 직원 확인이 필요한 강한 감정 추정에는 신규 일시정지 경로를 설계한다.
4. 밝거나 차분한 목소리, 개인의 평소 말버릇, 모델의 낮은 위험 점수로 명시적 위기 규칙을 무효화하지 않는다.
5. 출력 검사를 통과한 텍스트만 음성 합성·전달하는 구조를 유지한다.
6. 모델이 직접 권한·세션 상태·공식 기록 확정·보호자 공개를 변경하지 못한다.
7. 위기 대응·출력 검열·진단 표현 금지를 기관 설정으로 끌 수 있게 하지 않는다.
8. 기록의 진행자는 사람이며 AI 도구 사용 사실은 별도로 남긴다.
9. 기관·어르신별 접근 격리와 사용 권한·동의 검사를 유지한다.
10. ‘확인했다’와 ‘상황이 해결됐다’를 구분한다.

**정책 경계:** 현재 텍스트 규칙의 위기·급성 고통 중단과, 새 음성 감정 기반 일시정지는 별개다. ‘모든 부정적 감정을 일시정지로 통일’하는 변경은 합의되지 않았다.

〔편입 결정〕 전사 문맥 분류기도 같은 경계를 따른다: **규칙이 걸리면 즉시 종료(기존)**, 규칙은 안 걸리고 **분류기만 위기·고통으로 판단하면 직원 확인 일시정지(신규)**. 분류기 결과로 규칙 적중을 일시정지로 낮추지 않는다(D1·D3).

## 5. 현재 코드의 실제 동작

### 5.1 입력 검사

현재 중계는 Gemini Live가 반환한 입력 전사를 받으면 기존 전사와 이어 붙여 검사한다. 검사에는 공백·일부 문장부호를 제거한 텍스트와 어구 사전을 사용한다.

- 핵심 함수: assessUtterance()
- 매칭: normalized.includes(term)
- 분류: crisis / distress / rest_request / refusal / confusion / grief / silence / normal
- 위기 범주: self_harm / medical_emergency / abuse
- 위험 표시: none / grief / watch / crisis
- 최근 전사 누적 창: 저장 부분을 최근 4,000자로 제한
- 현재 중계 중단 조건: assessment.escalate 또는 assessment.hasDistressSignal
- 휴식·거부: 고정 마무리 인사 후 종료하는 별도 경로

‘none’은 위험 없음의 검증 결과가 아니라 등록 신호 미검출이다. ‘watch’라는 이름이 붙어도 급성 고통 표현은 현재 음성 중계에서 중단된다.

### 5.2 전사 시점의 한계

현재 음성은 Gemini로 전달된 뒤 입력 전사가 돌아와야 검사가 가능하다. ‘외부 모델에 음성을 보내기 전에 위험을 판정한다’는 구조가 아니다. 신규 자체 검사도 전사를 입력으로 쓰는 한 이 전사 지연과 인식 오류의 영향을 받는다.

### 5.3 현재 출력 검사

screenAiUtterance()가 의료 조언·진단, 교정·기억 시험, 모욕·유해 표현을 사전과 패턴으로 검사한다. 합성 직전에는 빈 문자열·길이 200 초과·일부 제어문자도 검사한다.

- Gemini 원본 음성은 앱으로 전달하지 않는다.
- 통과한 텍스트를 별도 TTS로 합성한다.
- 차단되면 현재 중계는 대체 문장으로 계속하기보다 오류 전달·연결 종료로 처리한다.
- 같은 검사가 서버·앱에 있어도 서로 독립적인 의미 판정 모델의 교차검증은 아니다.
- 합성된 음성을 다시 전사해 의미 일치를 검사하는 별도 경로는 현재 없다.

### 5.4 현재 음성 특징 처리

앱에는 PCM 음량 수준 계산과 발화 경계 제어가 있다. 현재 값은 발화 유무·종료 판단용이지 감정 점수가 아니다.

- 현재 앱 입력 경계: 발화 후 무음 약 3초, 처음부터 무입력 약 20초, 단일 입력 약 60초 상한
- 파일럿 세션 상한: 일시정지를 포함해 10분
- 중계 입력: 16kHz PCM
- 현재 코드에서 톤·속도·감정 분류를 완성된 기능으로 확인한 것은 아니다.
- 일반 로그에 원음·개별 전사·세부 음량을 무제한 저장하는 방식은 사용하지 않는다.

### 5.5 기존 대화에서 직접 확인한 예

| 입력 | 당시 현재 함수 결과 | 의미 |
|---|---|---|
| 숨을 쉴 수가 없어요. | normal | 등록 어형 밖의 표현 누락 |
| 가슴이 아파요. | grief | 신체 호소와 정서 표현의 실제 구별이 아님 |
| 옛날에 죽고 싶었던 적도 있어요. | crisis | 과거 시점 구별 부족 |
| 죽고 싶다는 생각은 안 해요. | crisis | 부정 문맥도 확인 대상으로 처리하는 기존 정책 |
| 할아버지는 그만하자고 말하셨어요. | rest_request | 인용·타인 발화 구별 부족 |
| 날 좀 내버려 둬요. | normal | 등록되지 않은 거부 표현 누락 |
| AI 응답: 병원에서 진단받으셨군요. | 차단 | 중립적 표현도 ‘진단’에 적중 |
| AI 응답: 영수 아드님이 어제 방문하셨군요. | 통과 | 사실성 검사가 아님 |

위 결과는 앞선 대화에서 실행한 기록이다. 임상 평가나 현장 정확도 수치가 아니며, 이번 문서 작성에서 신규 모델을 실행해 개선을 입증한 것은 아니다.

〔검토 반영〕 2026-11-13 최신 main(`d51c8b4`)에서 8개를 다시 실행해 **모두 위 표와 같음**을 확인했다. 그중 즉시 고칠 수 있는 미탐은 이 기획과 별개로 처리했다.
- "숨을 쉴 수가 없어요." → 기존 응급 사전에 `숨을쉴수가없`·`숨을쉴수없`·`숨쉴수가없`·`숨쉴수없`를 추가해 **crisis(medical_emergency)**. 회귀 2건 추가, 추가 구를 지우면 실패함을 확인. 중계 재배포·앱 재빌드 뒤 반영(`docs/tasks.md` SAFE-BREATH-20261113).
- "가슴이 아파요." → grief 는 **의도된 분류**다(`safety.ts` 응급 사전 주석: 정서 관용구 '가슴이 아파요'와 겹치지 않게 신체 위급 구만). 중계에서는 급성 고통도 즉시 종료이므로 옮기면 회상 중 "그 생각하면 가슴이 아파요"가 대화를 끊는다. 〔편입 결정〕 ✅ 2026-11-13 사용자 확정: **규칙은 그대로(grief)**. 회상 관용구와 현재 신체 호소("지금 가슴이 아파서 숨이…")를 문맥으로 가르는 것은 전사 문맥 분류기가 맡는다.

### 5.6 현재 일시정지·재개 구조 〔검토 반영〕

- 일시정지(현재는 감독 화면의 원격 일시정지)가 오면 중계는 진행 중 합성을 끊고 `relayControl: paused` 를 보낸 뒤 **공급자(Gemini) 연결과 앱 연결을 닫는다**(`relay.ts` `react`). 일시정지 중에는 마이크·전사·분석이 모두 멈춘다.
- 재개는 **새 연결**이다. 앱이 새 단기 토큰으로 다시 접속하며 **복구 맥락(v3 `resumeContext`)** 을 보낸다. 중계는 그 대화를 새 공급자 세션에 `clientContent` 로 넣은 뒤 이어 간다.
- 복구 맥락에 들어가는 것(`voice-context.ts` `selectVoiceResumeContext`): 어르신 발화 중 채택된 것(자동 전사 또는 요양보호사 확인) 전부 + AI 발화 중 **기기에서 끝까지 재생이 관찰된 것만**(중간에 끊긴 문장·재생 안 된 문장은 제외). 요약을 만들지 않고 원문 그대로다.
- 한도: 120턴·전체 16,000자. 넘으면 잘라서 이어 가지 않고 **재개가 실패**한다(조용히 일부를 버리지 않는다). 10분 세션 안에서는 닿기 어렵지만 감정 일시정지를 여러 번 거치면 확인이 필요하다.
- 확인하지 못한 것: 앱을 완전히 종료했다 다시 켠 뒤의 재개(로컬 상태 복원 여부)는 이번 대조 범위 밖이다(O20).

## 7. 전사 의미 기반 검사 설계

### 7.1 텍스트 임베딩의 역할

임베딩은 문장의 의미적 특징을 벡터로 표현한다. 임베딩만으로 위기 여부와 행동이 자동 확정되는 것은 아니다.

권고 구성:
- 문장·문맥을 인코딩하는 모델
- 필요한 범주를 판단하는 분류 헤드 또는 학습된 분류기
- 모델 결과와 기존 규칙을 받아 행동을 고르는 서버 정책

단순 유사도 검색은 관련 사례를 찾는 보조 수단으로 사용한다. ‘하고 싶다’와 ‘하고 싶지 않다’처럼 유사하지만 결론이 다른 문장을 최종 유사도 하나로 판정하지 않는다.

### 7.2 입력 구성

현재 전사, 직전 AI 질문, 최근 어르신 발화, 필요한 개인 맥락을 화자·턴별로 구분한다.

- 원문과 정규화문을 구분한다.
- 현재 검사 대상 턴을 명확히 표시한다.
- 개인 맥락에는 확인자·시점·출처·적용 범위가 있는 정보만 넣는다.
- 세션·기관·어르신·문맥 버전이 다른 판단을 재사용하지 않는다.
- 최근 대화의 길이와 최대 토큰 수는 미정이다.
- 과거 대화가 현재 안전 신호를 덮어쓰지 않도록 한다.

### 7.3 분류 항목 후보

| 항목 | 후보 값 | 상태 |
|---|---|---|
| 내용 | 위기 호소·정서적 고통·거부·휴식·회상·일상·불명 | 제안 |
| 위험 관련 범주 | 자해 관련·신체 응급 관련·학대 관련·없음·불명 | 기존 범주 확장 후보 |
| 주체 | 본인·타인·불명 | 제안 |
| 시점 | 현재·과거·미래·불명 | 제안 |
| 표현 방식 | 직접 호소·인용·가정·명시 부정·불명 | 제안 |
| 대화 의사 | 계속·전환 희망·휴식 희망·종료 희망·불명 | 제안 |
| 해석 가능성 | 정보 충분·부족·충돌·범위 밖 | 제안 |
| 근거 | 실제 턴·발췌·관련 맥락 ID | 제안 |

여러 항목은 동시에 존재할 수 있다. 휴식 요청과 고통 신호처럼 복합 발화를 하나의 상호배타 라벨로만 줄이지 않는다.

### 7.4 개인별 표현

공통 모델 + 확인된 개인 의미 자료를 기본 방향으로 제안한다. 어르신마다 LLM을 따로 학습하는 것은 기본안으로 채택하지 않았다.

개인 의미 자료 후보:
- 표현, 의미 후보, 관련 인물·장소·경험
- 사용 맥락, 원문 근거, 확인자·확인일
- 승인 상태·버전·유효 범위·수정/철회 정보

‘평소에도 그런 말을 한다’는 이유로 명시적 위험을 무효화하는 예외 목록을 만들지 않는다. 직원의 추측과 어르신 본인의 설명도 구분한다.

## 8. 음성 관찰 특징

### 8.1 측정할 값과 해석을 분리한다

| 특징 | 측정 정의 후보 | 해석 시 고려 |
|---|---|---|
| 전체 발화 속도 | 전사 음절/전체 발화 구간 시간 | 침묵과 STT 오류 영향 |
| 발성 중 속도 | 전사 음절/실제 발성 구간 시간 | VAD와 구간 정렬 필요 |
| 응답 지연 | AI 재생 종료 관찰~어르신 발화 시작 | 실제 청취·이해 완료 증거와 구분 |
| 침묵 | 구간 수·총 길이·최장 길이·직전 대비 변화 | 생각·청력·네트워크·거부 등 여러 원인 |
| 음높이 F0 | 유성 구간의 중앙값·범위·변동 | 무성음·작은 소리·소음에서는 산출 불가 가능 |
| 상대 음량 | RMS·변화량 등 | 실제 음압과 다름. 거리·자동 이득 영향 |
| 억양 변화 | F0 윤곽·문장 끝 변화·기울기 후보 | 단일 값으로 감정 확정 불가 |
| 발성 지속·끊김 | 구간 길이·짧은 발화의 반복 | 건강·습관·녹음 실패와 구별 |
| 겹침·잡음 | 잡음·다중 화자·에코 신호 후보 | 어르신 감정 자료에서 제외/보류 필요 |
| 울음·웃음 등 | 음성 이벤트 모델 후보 | 톤만으로 확정하지 않음. 별도 검증 필요 |

음절 산출 규칙, 발성·침묵 정의, 정렬 방법, 샘플링 창은 모두 미정이다. 음악용 tempo 값을 그대로 사람의 발화 속도로 사용하지 않는다. F0 미산출은 0Hz나 감정 저하로 바꾸지 않고 null로 둔다.

### 8.2 개인 기준선

권고는 동일 어르신·동일하거나 비교 가능한 입력 조건의 평소 특성과 비교하는 것이다.

- 초기 기준선이 없으면 ‘기준선 부족’으로 표시한다.
- 기기·마이크·마이크 거리·소음·녹음 설정 변경을 기록한다.
- 심한 잡음·다중 화자·위기·감정 변화 구간을 정상 기준선에 자동 혼합하지 않는다.
- 한 세션의 큰 변화로 장기 기준선을 즉시 덮어쓰지 않는다.
- 나이·성별 평균만으로 개인을 정상/비정상으로 분류하지 않는다.
- 기준선 최소 자료량, 갱신 주기·가중치·보관기간은 미정이다.

### 8.3 품질 게이트

TV나 직원의 목소리를 어르신 감정으로 저장하면 학습 자료가 오염된다. 화자·에코·소음 품질이 불충분하면 감정 해석을 보류한다.

현재 AEC와 입력 검출 기반이 있어도, 화자 분리와 감정 입력 품질 검증이 완료됐다는 뜻은 아니다. 화자 임베딩을 도입할지, 직원 수동 구간 확인을 사용할지, 제3자 음성을 어떻게 제외할지는 미정이다.

## 9. 음성 감정 예측

### 9.1 출력 후보

슬픔·분노·두려움/불안·긍정적 반응·중립·기타·불명 등의 후보를 고려한다. 최종 범주와 한국어 명칭은 미정이다. 동시 감정과 불확실성을 허용하는 방향을 제안한다.

일반적인 감정 모델의 범주가 기억온의 ‘직원 개입 필요’와 동일한 것은 아니다. 사용 모델의 라벨 정의를 먼저 확인해야 한다.

### 9.2 점수의 의미

다음은 서로 다른 값이다.

1. 분노 범주에 가깝다는 모델 점수
2. 음성의 각성·강도 관련 특징
3. 실제 감정 강도
4. 대화를 계속하기 어려운 부담
5. 직원 확인의 긴급성

분노 점수가 높다는 이유만으로 ‘매우 심한 분노’라고 표시하지 않는다. 감정 강도와 지원 필요 수준은 별도 정의·자료·검증이 필요하다. 점수를 위험 확률이나 임상 점수로 표시하지 않는다.

### 9.3 후보 모델

emotion2vec 계열은 음성 감정 표현·분류 후보다. 공개 모델이 있다는 사실은 한국어 고령자 자료의 성능을 보증하지 않는다. 모델별 크기·연산량·라이선스·상업적 활용 조건·학습 자료 출처를 확인해야 한다.

서버 내부 직접 실행이 기본 제약과 맞지만 최종 모델·크기·CPU/GPU·양자화·추론 주기는 미정이다. 자동 다운로드나 외부 음성 업로드 경로 없이 운영할 수 있는 패키징을 검토한다.

## 10. 관찰·추정·본인 의사·직원 관찰의 분리

| 층 | 예 | 기록 원칙 |
|---|---|---|
| 관찰 | 침묵 증가·상대 음량 상승 | 산출 방식·구간·버전 기록 |
| 모델 추정 | 슬픔 가능성 | 점수·불확실성·모델 출처 |
| 본인 의사 | 계속 말하고 싶다·쉬고 싶다 | 실제 발화 근거 |
| 직원 관찰 | 즐겁게 회상하던 상황으로 보임 | 확인자·시각·의견 기록 |
| 최종 조치 | 일시정지·재개·종료 | 정책 버전·권한·실행 결과 |

직원이 ‘괜찮아 보인다’고 평가한 내용도 내면 감정의 절대 정답은 아니다. 출처가 다른 판단을 하나의 사실로 합치지 않는다.

## 11. 통합 판단과 정책 우선순위

아래는 제안이며 임계값은 정하지 않았다.

1. 기존 명시 위기·급성 고통 종료 규칙을 우선 집행한다.
2. 명시적인 종료·휴식·거부 의사는 현재 경로에 따라 존중한다.
3. 품질이 나쁜 음성의 감정 결과는 보류한다.
4. 전사 의미·음성 관찰·감정 후보·개인 기준선·본인 의사를 함께 검토한다.
5. 지원 필요 수준과 행동을 구분한다.
6. 강한 감정만 추정되는 신규 경로에서는 사용자 합의대로 일시정지·직원 확인을 적용한다.
7. 이후 조치는 권한 있는 직원의 확인을 거치도록 제안한다.

기존 규칙과 신규 모델을 단순 평균해 점수가 낮아지면 위기를 해제하는 방식을 사용하지 않는다. 전사·음성 신호가 충돌하면 충돌 상태를 기록하고, 안전으로 자동 단정하지 않는다.

〔편입 결정〕 규칙 × 전사 문맥 분류기의 결합은 **OR**(D1)이고, 결합 정책은 `packages/core` 의 순수 함수로 두어 진리표 테스트로 고정한다(개발 범위 — `docs/tasks.md` CTX-CLS-20261113 S4). 미정 칸(아래 표의 "미정")은 그 함수에서도 임의 기본값으로 채우지 않는다.

## 12. 부정적 감정과 대화 조절

사용자 목적은 부정적 감정을 포착하고 적절히 대화에 반영하는 것이다. 그 목적을 다음 동작으로 구체화하는 방안을 제안한다.

- 기다리는 시간을 조절한다.
- 질문을 짧고 쉽게 바꾼다.
- 한 번에 하나의 질문을 유지한다.
- 어르신 말을 짧게 공감한다.
- 계속 이야기할지, 다른 이야기로 바꿀지, 쉴지 의사를 살핀다.
- 요청·심한 고통 신호에는 적절한 중단 경로를 사용한다.

슬픔·애도를 무조건 실패로 보고 밝은 주제로 돌리지 않는다. 어르신이 원해서 기억을 나누는 상황에서는 공감과 자기결정을 우선한다. ‘감정 점수를 긍정으로 올리기’를 제품의 최적화 목표로 두지 않는다.

### 12.1 대응 예 — 실제 운영 성과가 아닌 설계 사례

| 상황 | 대응 예·주의 |
|---|---|
| 가족을 그리워하고 계속 말하고 싶어 함 | “가족분들이 많이 보고 싶으셨겠어요. 조금 더 이야기 나누실까요?” |
| 질문 때문에 불편함을 표현함 | 질문 부담을 낮추거나 전환 의사를 확인. 명시 거부면 기존 마무리 경로 |
| 조용한 목소리지만 원래 말투이고 참여 지속 | 작은 목소리만으로 슬픔·위험 판정하지 않음 |
| 빠른 말·큰 소리로 즐겁게 과거 이야기 | 분노로 단정하지 않고 내용·개인 특성을 함께 봄 |
| 현재 응급 호소와 차분한 목소리 | 목소리를 이유로 위험 중단을 취소하지 않음 |
| 울음 추정·응답 단절·진행 어려움 | 품질 확인과 직원 확인 경로. 확정되지 않은 울음을 사실로 기록하지 않음 |

## 13. 감정 기반 일시정지와 직원 확인

### 13.1 확정된 방향

사용자는 ‘잠시 멈추고 직원이 확인하는 방식’을 선택했다. 이 문서에서는 신규 감정 기반 대응의 중심으로 둔다.

〔편입 결정〕 이 경로의 **첫 사용처는 전사 문맥 분류기의 단독 적중**이다(D3 — 파일럿 안, 게이트 통과 시). 음성 감정 기반 일시정지는 파일럿 이후 그대로다. 따라서 시스템 원인 일시정지 기록(§14.1 — 중계 전용 서버 자격)과 O17·O19 결정이 분류기 투입의 선행 조건이 된다.

### 13.2 제안하는 처리

1. 세션·턴에 연결된 판단 근거와 사건 ID를 만든다.
2. 새 질문·합성·오디오 전달을 멈추고 이미 전달된 오디오의 중단을 요청한다.
3. 서버 상태를 일시정지로 기록하는 경로를 설계한다.
4. 직원 앱·웹에 확인 요청을 표시한다.
5. 직원 확인·조치를 기록한다.
6. 권한 있는 직원이 재개·휴식·종료 등을 선택한다.
7. 재개 시 실제 전달된 대화 맥락과 서버 상태를 맞춘다.

〔검토 반영〕 **2026-11-13 사용자 확정: 일시정지 중에는 듣지 않는다.** 현재 구조(§5.6)처럼 연결을 닫고, 재개 때 새 연결 + 복구 맥락으로 다시 연다. 따라서 일시정지 중 새 위험 발화는 자동 탐지되지 않는다 — 이 운영 특성을 직원 화면·안내 문구에 명시한다(O12·O13).

시간 경과만으로 자동 재개하지 않는 방향을 권고한다. 이는 추가 제안이며 재개 정책 확정이 필요하다.

### 13.3 직원 화면 후보

- 상태: 대화 상태 확인 필요
- 실제 관찰: 음량·속도·침묵 변화와 품질 상태
- 모델 해석: 감정 후보·불확실성
- 관련 전사: 접근 권한 아래 최소 근거 표시
- 감지 경로: 기존 규칙 / 전사 분류 / 음성 감정 / 복합 / 시스템 오류
- 저장 상태: 기록 완료 / 진행 중 / 실패
- 선택 후보: 그대로 재개 / 주제 바꾸고 재개 / 휴식 유지 / 종료

감정 점수 하나만 강조하지 않는다. ‘위험 확정’과 같은 표현 대신 확인 요청의 이유를 제시한다. 구체 UI·문구·버튼·권한은 미정이며 기존 디자인 언어를 따른다.

### 13.4 확인과 해결

수신·화면 열람·확인·현장 확인·조치·재개·해결은 서로 다른 사건이다. 확인 버튼으로 나머지 단계를 자동 완료하지 않는다.

직원 의견 후보:
- 공감하며 계속 가능한 상황
- 질문·소재 전환이 필요한 상황
- 휴식이 필요한 상황
- 종료·추가 확인이 필요한 상황
- 기기·소음 문제
- 판단 어려움
- 기타 의견

최종 입력 항목과 필수 여부는 미정이다. 직원에게 매 턴 긴 라벨링을 요구하는 제품으로 만들지 않도록 한다.

## 14. 상태 모델 후보

다음 이름은 설계용이며 기존 DB enum에 존재한다는 뜻이 아니다.

| 후보 상태 | 의미 |
|---|---|
| running | 정상 진행 |
| checking | 현재 입력의 신규 검사 대기 |
| emotion_pause_pending | 감정 기반 일시정지 적용 중 |
| paused_for_staff | 직원 확인을 기다리는 일시정지 |
| staff_reviewing | 직원이 확인 중 |
| resuming | 권한·동의·문맥을 재확인하며 재개 |

| crisis_terminated | 기존 위기 종료를 표현하는 설계상 결과 |
| degraded | 모델·입력·통신 문제로 정상 진행 곤란 |

실제 구현에서는 기존 sessions.status·phase·paused_at·제어 RPC와 조합할지 별도 사건 상태를 둘지 결정해야 한다.

### 14.1 현재 DB와의 차이

- 현재 원격 일시정지의 사람 actor와 신규 시스템 감지 origin은 구분해야 한다.
- 자동 일시정지를 직원이 직접 눌렀다고 기록하지 않는다.
- 시스템 사건에 직원 ID를 임의로 넣지 않는다.
- 기존 session_interventions의 action 집합을 임의 확장한 것으로 가정하지 않는다.
- 시스템 일시정지를 허용할 신뢰된 서버 경로·권한 계약이 필요하다.
  - 〔검토 반영〕 현재 중계는 보안상 관리자 키(service_role) 없이 **직원 로그인 토큰으로만** DB를 부른다. 같은 방식인 `record_elder_closing`(T21.11)은 DB 입장에서 "중계가 보냈다"와 "직원이 직접 보냈다"를 구분하지 못한다.
  - **2026-11-13 사용자 결정: (나) 중계 전용 서버 자격을 둔다.** T23.5 의 `VOICE_RELAY_SECRET`(`live-token` 전용)과 같은 발상으로, 시스템 원인 기록 RPC 는 중계 자격이 있을 때만 받는다. 자격 저장 위치(Secret Manager)·DB 쪽 검증 방식·교체 절차·직원 토큰과의 결합 방식은 구현 설계에서 정한다(O39).
- 기본 10분 상한은 일시정지를 포함한다. 새 확인 대기 시간을 제외하도록 바꾸는 결정은 없었다.

## 15. 출력 검사와 대화 모델의 관계

입력 위험·감정 해석과 AI 출력 검사는 분리해 유지한다.

- 입력이 평온하다고 AI 응답을 무검사로 재생하지 않는다.
- ‘공감’ 행동이 선택돼도 의료 조언·모욕·기억 시험 표현을 차단한다.
- 감정 후보를 어르신에게 단정적으로 말하지 않는다.
- 어르신이 모르는 시스템 분류를 소리 내어 읽지 않는다.
- 명확한 위험에서 대화 모델이 상담을 계속하도록 하지 않는다.
- 출력 의미 검사와 사실 근거 검사는 별도 문제다.
- 신규 출력 의미 모델 추가 여부·검사 범위는 미정이다.

## 16. 지연·비용·배포

### 16.1 확정 제약

추가 외부 AI 검사 API에 의존하지 않는 방향이다. 기존 Gemini 대화·전사·TTS 사용을 모두 제거한다는 결정은 아니다.

### 16.2 권고 운영

- 초기에는 현재 중계와 가까운 자체 실행 환경을 우선 비교한다.
- 모델은 프로세스 시작 때 준비하고 메모리에 유지한다.
- 음성·텍스트 처리와 분류를 가능한 범위에서 병렬 실행한다.
- 모델 계산이 음성 송수신·서버 시간 관리·긴급 중단을 막지 않도록 실행 자원을 분리한다.
- 동시 실행·큐 길이·메모리·시간 상한을 관리한다.
- 모델·토크나이저·특징 추출기·정책 버전을 함께 고정한다.
- 모델 교체·양자화 뒤 별도로 품질을 평가한다.
- 새 외부 검사 API 토큰 요금은 없지만 자체 CPU/GPU·메모리·운영 비용은 발생한다.

### 16.3 검사 시점

긴급한 기존 규칙은 지연시키지 않는다. 음성 특징·감정 분석은 안정된 구간 또는 발화 단위로 수행하는 후보가 있다. 모든 PCM 조각마다 무거운 모델을 실행하는 구성을 기본으로 두지 않는다.

부분 전사의 조기 결과는 잠정값으로 취급해야 한다. 나중에 ‘안 해요’가 붙는 것처럼 의미가 바뀔 수 있다. 어떤 행동을 부분 결과만으로 허용할지 미정이다.

### 16.4 재생 허용 장벽

검사 결과를 기다리지 않고 음성을 먼저 재생해 지연을 숨기지 않는다. 결과에는 sessionId·turnId·inputRevision·contextVersion을 연결한다. 이전 턴·회수된 연결 세대의 허용 결과가 다음 응답을 승인하지 못하게 한다.

모델 오류·시간 초과·음질 불량을 안전 판정으로 바꾸지 않는다. 이때 직원 확인·재확인·종료 중 어떤 동작을 사용할지 별도로 정한다. 모든 분석 지연을 0으로 만드는 약속은 하지 않는다.

〔검토 반영〕 **2026-11-13 사용자 확정 — 검사를 두 종류로 나눈다.** 응답 지연은 이미 실기기에서 지적된 문제(2026-10-16)라 모든 검사가 재생을 막으면 악화된다.

| 종류 | 대상 | 재생과의 관계 |
|---|---|---|
| 재생을 막는 검사 | 기존 규칙(`assessUtterance`·`screenAiUtterance`) + 소형 텍스트 분류기(목표: 수십 ms급) | 통과해야 합성·재생 |
| 비동기 검사 | 음성 특징·감정 모델 | 재생을 기다리게 하지 않는다. 결과는 **다음 턴을 시작하기 전** 일시정지 판단에만 쓴다 |

비동기 결과가 늦게 도착해도 이미 지난 턴을 되돌리지 않는다. 같은 `sessionId`·`turnId`·연결 세대에 묶인 결과만 다음 턴 판단에 쓴다.

### 16.5 서버 자원과 확장 〔검토 반영〕

현재 중계(런북 배포 명령 기준 — 실제 서비스 값은 Cloud Run 콘솔에서 확인): **최대 1대 · 메모리 미지정(Cloud Run 기본 512MiB) · CPU 기본 1 · CPU 항상 할당 · 프로세스당 음성 연결 4개 · Node 단일 프로세스**.

확장으로 해결되는 것과 안 되는 것:

| 방식 | 해결되는 것 | 해결되지 않는 것 |
|---|---|---|
| 수직 확장(한 대의 메모리·CPU 상향) | 모델 적재 메모리(감정 모델 large 급은 가중치만 약 1GB 이상이라 현 사양에 안 올라감) · 한 번의 추론 시간 일부 | 같은 Node 프로세스에서 추론하면 권한 확인(2초 폴)·위기 즉시 중단이 그 계산 동안 늦어질 수 있음 → **추론은 별도 스레드나 보조 컨테이너로 분리 필수** |
| 수평 확장(대수 증가) | 동시 세션 수. 같은 세션의 중복 점유는 DB 점유(T26.1)가 막으므로 구조상 가능 | 발화 1건의 추론 지연(대수를 늘려도 한 건은 빨라지지 않음) |
| GPU | 추론 지연 | 서울 리전 지원 여부·비용은 미확인 |

비용: 업무 시간에는 1대가 항상 떠 있어(최소 인스턴스 1) 사양을 올린 만큼 **상시 비용**이 늘고, 대수를 늘리면 그 배수로 는다. 최종 사양은 모델 선택(O30·O31) 뒤 실측으로 정한다(O35·O36).

## 20. Qwen 대화 특화 학습

### 20.1 먼저 학습할 문제

원음에서 감정 이름을 맞히는 문제와, 상황에 맞는 대화를 생성하는 문제를 나눈다.

- 음성 모델: 음성의 표현 특징·감정 후보를 산출
- 전사 분류기: 의미·주체·시점·의사·불확실성을 분류
- Qwen 대화 모델: 허용된 상태 정보와 대화 맥락을 바탕으로 질문·공감·대화 방향을 제안
- 서버 정책: 실제 중단·직원 호출·재개·권한을 집행

Qwen이 좋다고 판단해도 기존 위기 중단·사람 확인 경로를 우회하지 않는다.

### 20.2 권고 초기 경로 — 텍스트 Qwen

전사와 다음 정보를 짧고 일관된 형식으로 제공한다.

1. 최근 대화와 확인된 개인 맥락
2. 입력 품질·관찰 가능한 음성 특징
3. 감정 후보와 불확실성
4. 본인의 계속/전환/휴식 의사
5. 서버 정책이 허용한 대응 범위
6. 사람이 검토한 적절한 행동·응답

일반 텍스트 Qwen에 임의의 음성 임베딩 실수 벡터를 문자열로 넣으면 의미를 자동 이해한다고 가정하지 않는다. 초기에는 해석 가능한 특징·상태를 구조화해 제공한다. 벡터를 직접 연결하는 방식은 별도 어댑터·멀티모달 학습 경로다.

### 20.3 선택지 — 음성 입력 Qwen

Qwen-Omni 계열처럼 음성 입력을 지원하는 모델을 비교할 수 있다. 다만 텍스트 Qwen과 다른 입력·학습·서빙 구조이며, 한국어 고령자 성능이나 기존 비용 조건 충족을 보증하지 않는다. 최종 모델 계열·규모·체크포인트는 미정이다.

### 20.4 학습 단위

‘발화 → 감정’ 한 쌍보다 다음 연결을 기본 단위로 제안한다.

> 직전 대화 + 현재 전사 + 정렬된 음성 특징 + 추정의 불확실성 + 본인/직원 관찰 + 선택한 대응 + 실제 전달 응답 + 이후 반응

AI가 생성했지만 재생되지 않은 문장을 실제 대화로 학습하지 않는다. 중간 중단된 발화는 완료된 발화와 구분하고, 정확한 재생 범위를 모르면 그 사실을 남긴다.

### 20.5 학습 목표 후보

- 긴 침묵에 성급히 질문을 덧붙이지 않기
- 대화 부담이 커질 때 질문을 짧고 쉽게 하기
- 반복을 지적하거나 기억을 시험하지 않기
- 애도·분노의 서사를 무조건 회피하지 않기
- 전환·휴식에 관한 본인 의사를 존중하기
- 명확한 위험에서 상담을 계속하지 않기
- 감정을 단정하거나 진단하지 않기
- 정보가 부족하면 확인하거나 직원 경로로 넘기기
- 공감·전환 제안을 맥락에 맞는 짧은 문장으로 하기
- 직원 개입 이후 복귀 맥락을 정확히 다루기

### 20.6 단계 후보

1. 독립적으로 작성·검토한 예시와 허용된 자료로 기준선 구성
2. 조회·프롬프트만 적용한 텍스트 Qwen 기준선 평가
3. 같은 조건의 SFT/LoRA 후보 평가
4. 검토된 선호 자료가 확보되면 선호 학습 비교
5. 가려진 현장 조건의 shadow 평가
6. 승인된 제한 범위에서 전환 여부 판단

학습 방법·도구·GPU·데이터 규모·일정은 미정이다. 프롬프트와 조회만으로 충분한 부분까지 무조건 파인튜닝하지 않는다.

### 20.7 실패 자료

유용한 실패 사례는 다음과 같다.

- 즐겁게 강조한 발화를 분노로 추정
- 조용한 평소 말투를 슬픔으로 추정
- 직원/TV 음성을 어르신 감정으로 추정
- 과거 회상을 현재 위기로 오해
- 명시 위험을 평온한 목소리 때문에 낮게 해석
- 공감 후 계속하고 싶다는 의사를 무시하고 전환
- 질문 난도를 높여 응답이 끊김
- 직원이 오류를 수정했는데 이전 잘못된 상태가 재사용됨
- 분석 시간 초과로 부적절하게 통과·반복 중단
- 생성한 응답과 실제 전달된 응답이 다름

실패 자료도 허용된 수집·학습 범위 안에서만 사용한다.

## 21. 정답·라벨·개인정보와 공급자 계약

### 21.1 라벨 출처 구분

| 라벨 출처 | 의미 | 취급 |
|---|---|---|
| 자동 감정 모델 | 모델이 산출한 후보 | 참값으로 확정하지 않음 |
| 어르신 본인 표현 | 그 순간의 자기 보고·의사 | 원문·시점과 함께 보존 |
| 직원 관찰 | 관찰자의 판단 | 주관성과 출처 기록 |
| 독립 검수자 | 정해진 규약에 따른 해석 | 불일치·보류 허용 |
| 이후 반응 | 실제 다음 반응의 관찰 | 해당 응답이 효과의 원인이라는 단정과 구분 |

모델 점수와 직원 판단을 섞어 ‘정답 감정’ 하나로 덮어쓰지 않는다. 직원이 잘못된 감정을 정정하는 경우도 원 추정과 정정을 함께 보존한다.

### 21.2 동의와 목적

기존 프로젝트 정책대로 기본 서비스 처리와 선택적 학습 참여를 구분한다. 감정 추정·음성 특징·개인 기준선·원음 보유의 목적과 항목을 함께 검토한다.

- 학습 거부가 기본 서비스 이용 불가로 이어진다는 전제를 두지 않는다.
- 본인과 적법한 대리 권한을 구별한다.
- 목적·항목·기간·접근자·철회 절차를 정한 후 학습 자료 수집을 시작한다.
- 화자 식별 기술을 추가하면 별도 민감성·필요성 검토가 필요하다.
- 외부 라벨러, 제3자 음성, 가족 정보 처리 방식을 정한다.
- 서비스 동의 문서를 임의로 수정하지 않고 기존 법무 검토 절차를 따른다.
- 〔검토 반영〕 **법무 검토 요청 대상** — 최종 항목은 사용자가 명시하고 변호사 미팅에서 확인한다(2026-11-13). 검토 때 나온 후보: 감정 추정은 기존 별도 동의(민감정보 — 건강·음성)의 목적 밖일 수 있다 · 화자 검증을 넣으면 생체인식정보(민감정보) 처리가 될 수 있다 · 학습 목적 동의와 대리 동의 · 법률 문서(`apps/web/src/content/legalDocuments.ts`)는 수정하지 않는다.

### 21.3 공급자 출력·학습 권리

Gemini 자동 전사·응답·수정본·파생 자료가 자체 Qwen 학습에 자동으로 사용 가능하다고 가정하지 않는다. 실제 적용 계약과 자료 출처를 확인해야 한다.

프로젝트의 기존 원칙은 계약 확인 전 Gemini 참여 출력·파생 자료의 학습 제외다. 이번 문서도 그 제한을 유지한다. 독립 원음 수집·사람 전사·독립 작성 응답을 우선 경로로 검토하되, 자료별 권리는 별도로 확인한다.

원음을 특징으로 변환했다고 공급자 계약·동의 제한이 없어지는 것은 아니다. 제안하는 저장 구조는 ‘학습 후보’와 ‘학습 허용’을 분리해야 한다.

### 21.4 보관·삭제·철회

원음·전사·음성 특징·감정 후보·개인 기준선·직원 관찰·모델 체크포인트별 기간은 미정이다.

자료-데이터셋-모델 버전의 계보를 남기고, 철회 시 신규 수집·향후 학습 제외·허용 범위 삭제·이미 학습한 모델의 영향 처리를 구분한다. 가중치에서 개인 영향을 즉시 지운다고 보장하지 않는다. 백업 복원 후 삭제 정보 재적용도 필요하다.

DB·중계의 서울 위치와 기존 외부 AI 처리 위치는 구별한다. 신규 자체 분석은 국내 운영 방향을 우선 검토하되 실제 배포·저장·백업·검수 위치를 각각 확인한다.

### 25.1 〔편입 결정〕 전사 문맥 분류기 — 파일럿 안 개발 경로

위 P1~P7 중 **전사 문맥 분류기 부분만** 파일럿 안으로 당긴다(D2). 실행 상태는 `docs/tasks.md` CTX-CLS-20261113 이 SoT 다.

| 단계 | 산출물 |
|---|---|
| S0 | 문서 정합(이 절) |
| S1 | 라벨 규약 + 자료 틀(시범 예시) |
| S2 | 평가 자료 확정 + **현재 규칙 기준선**(같은 평가 자료로 범주별 재현율·정밀도·오탐) |

| S4 | 결합 정책 순수 함수(core) + 진리표 테스트 |
| S5 | ONNX·int8·Node 추론 패키지(worker_threads)·Python↔JS 토크나이저 일치 · Cloud Run 동등 조건 지연·메모리 실측 |
| S6 | 개인 의미 자료·시스템 원인 일시정지 DB 설계(사용자 승인 뒤 마이그레이션 + RLS 회귀) |
| S7 | **투입 게이트 보고서** + 중계 통합 인계 자료 |

**투입 게이트**: 보고서는 범주별 "규칙 단독 vs 규칙 OR 분류기"의 재현율·정밀도·미탐 사례, 분류기 단독 적중에 따른 불필요한 직원 확인 일시정지 추정, 문맥 축(주체·시점·부정·인용·관용)별 오류, 양자화 전후·하위군 차이, Cloud Run 동등 조건 P50/P95 지연·메모리를 제시한다. **합격 수치는 사용자가 정한다(미정 — O51·O53)**. 평가 자료가 작성된 예시라는 한계를 함께 적고, 자동 테스트·평가 수치를 현장 합격으로 표현하지 않는다.

**범위 밖**: 중계(`apps/voice-relay`)에 실제로 연결하는 작업은 게이트 보고서 뒤 중계 담당 작업으로 따로 진행한다. 운영 DB 쓰기·배포는 사용자 승인 사항이다.

## 27. 발표·사업 문서에 사용할 수 있는 설명

다음은 개발 방향을 설명하는 문장이다.

> 기억온은 발화 전사의 의미와 대화 맥락을 분류하고, 목소리의 속도·톤·침묵 같은 관찰 신호를 결합하는 안전 검사 구조를 설계하고 있습니다. 위기 신호와 어르신의 의사를 정해진 대응 규칙에 연결하고, 강한 감정으로 직원 확인이 필요한 상황에서는 대화를 일시정지하는 방향입니다. 이 과정의 관찰·직원 판단·이후 반응을 분리해 축적하여, 향후 Qwen 기반 대화 모델의 질문·공감·전환 방식을 학습하는 데 활용할 계획입니다.

현재 코드의 등록 표현 검사와 신규 설계를 구분한다. 감정 예측을 실제 감정 확정·의료적 진단·모든 위험 탐지·상용화된 자체 모델로 표현하지 않는다. 학습 이용이 허용된 자료라는 범위도 유지한다.

### 28.2 후보·기술 자료

다음은 구성 가능성과 도구의 성격을 확인하는 1차 자료다. 기억온의 고령자 감정·안전 성능을 입증한 자료는 아니다.

- [KoELECTRA 공식 저장소](https://github.com/monologg/KoELECTRA): 한국어 기반 분류 모델 후보의 출발점.
- [KLUE RoBERTa 공식 모델](https://huggingface.co/klue/roberta-base): 한국어 문맥 모델 비교 후보.
- [SetFit 공식 문서](https://huggingface.co/docs/setfit/index): 문장 모델을 이용하는 분류 학습 접근. 자료 효율에 관한 일반 결과를 현장 안전성에 전용하지 않는다.
- [emotion2vec 공식 모델 카드](https://huggingface.co/emotion2vec/emotion2vec_plus_large): 음성 감정 표현·분류와 발화/프레임 단위 출력 후보. 모델 라이선스는 별도 확인한다.
- [ONNX Runtime 양자화 문서](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html): 자체 추론 최적화 후보. 양자화에 따른 품질 변화 확인 필요.
- [Qwen3-Omni 공식 저장소](https://github.com/QwenLM/Qwen3-Omni): 음성 입력 모델 경로와 텍스트 모델 경로의 구분 근거.
- [Gemini API 추가 약관](https://ai.google.dev/gemini-api/terms): 실제 적용 서비스·계약별 학습 활용 범위 확인 자료. 기존 프로젝트의 계약 확인 전 학습 제외 정책을 유지한다.

외부 자료는 2026-11-13 작성 시 다시 열어 확인했다. 모델·라이선스·계약·도구 버전은 구현 시 선택한 실제 버전을 기준으로 재확인한다.
