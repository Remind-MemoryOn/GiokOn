## 1. 웹 AI 에이전트 추가
- **내용**: 웹에 AI 에이전트. ⓐ 요양보호사 — 업무 보조. ⓑ 보호자 — 건강 분석·기록 요약 등 데이터 이해 보조. (초기 범위는 여기까지.)
- **반영 방식(초안)**: Edge Function + LLM(Structured Outputs), `core`/`data` 재사용. 역할별 컨텍스트 분리(요양보호사=관리 도구 / 보호자=열람 데이터 설명).
- **필요성·검증**: ✅ 필요. 기존 **M18(AI 에이전트)** 트랙과 정합. 인터뷰가 유스케이스를 구체화(보호자용 설명 에이전트는 M18 원안[요양보호사 전용]에 **추가된 새 각도**).
- **기존 매핑**: M18(웹 에이전트).
- **⚠️ 플래그**: 보호자용 "건강 분석" 설명은 **비의료 경계** 위험 — 진단·판정이 아니라 **관찰 지표 요약**으로 프레이밍해야 함(효능·병증 단정 금지). 에이전트는 **커밋된 데이터만** 근거로(RLS).

## 2. 초기화면 + 인증 + 보호자 접근통제 (보안·필수)
- **내용**:
  - 현재 문제(무조건 수정): ⓐ 보호자 세션이 **로그인 없이 접근** 가능, ⓑ 본인과 무관한 어르신 데이터까지 접근 가능.
  - 초기화면 = 서비스 소개 + 로그인 버튼. 로그인 정보(역할)에 따라 **요양보호사/보호자 페이지로 자동 라우팅**.
  - 보호자는 **본인과 연결(요양보호사 승인)된 어르신 데이터만** 접근.
  - 승인 경로: **QR코드 / 요양보호사에게 요청** 등 → 결국 **요양보호사 승인**이 있어야 접근 가능.
- **반영 방식(초안)**: 랜딩 재작성(소개+로그인). 보호자 = **Supabase Auth(role=guardian)** 실계정. 로그인 후 역할 기반 리다이렉트. `profile_guardians`(환자↔보호자 연결·상태 pending/approved) + RLS로 **승인된 어르신만** 노출. 승인 UX = 요양보호사가 초대(QR/코드) 발급 → 보호자 연결 요청 → 요양보호사 승인.
- **필요성·검증**: ✅ **최우선 필수(보안·개인정보)**. 현재 웹의 데모 보호자 로그인(무인증·아무 어르신 선택)은 실제 취약점. 반드시 교체.
- **기존 매핑**: M17.1(`profile_guardians`)·M17.3(보호자=Auth role=guardian, 커밋 데이터만) + 조직 RLS. 인터뷰가 **승인 UX(QR/요청)** 를 구체화.
- **⚠️ 플래그**: 보호자 회원가입·본인확인 수준(어디까지 검증?) 결정 필요. QR vs 요청 방식 택1 또는 병행 결정 필요.

## 3. 요양보호사 페이지 신규 기능
### 3-1. 요양일지 작성 (현직자 최대 요청) — 신규
- **내용**: 수기 일지를 **사진 촬영 업로드 / 직접 타이핑 / 구어(음성) 입력**. **AI 에이전트 적극 활용**(일지 작성이 1순위 니즈).
- **반영 방식(초안)**: `care_journals` 테이블 + 입력 3경로 — 사진(비전/OCR로 텍스트화) · 음성(STT) · 텍스트. AI 에이전트가 원문 → 구조화 일지 초안 작성. 사진은 Storage.
- **필요성·검증**: ✅ 필요(채택 좌우하는 핵심 니즈). **현 계획에 없던 신규 기능** — 가장 큰 스코프 추가.
- **기존 매핑**: 신규(M16/M17과 별개). 입력 파이프라인은 앱의 STT/비전 인프라와 공유 가능.
- **⚠️ 플래그**: 일지에 **건강 관련 민감정보** 포함 가능 → 동의·RLS·보관파기 적용. 비전 OCR 방식(LLM 비전 vs 전용 OCR) 결정 필요. 비의료 프레이밍 유지.

### 3-2. 데이터 공개 체크리스트 — (M17 커밋 워크플로 확정)
- **내용**: 요양보호사가 관리하는 데이터(일지·특이사항 등) 중 **오늘 어떤 것을 연결된 보호자에게 공개할지 체크리스트**로 선택 → "공개하기" → 보호자 웹에 노출. AI 에이전트가 요청 시 **대신 공개** 수행.
- **반영 방식(초안)**: `guardian_shares`(커밋 항목·대상 보호자·유형·승인자·시점·철회) + 체크리스트 UI + 감사로그. 에이전트 tool로 공개 실행(사람 확인 후).
- **필요성·검증**: ✅ 필요. 이건 우리가 설계한 **보호자 공유 커밋(M17)** 을 현직자가 **그대로 확인**해 준 것 — 강한 검증.
- **기존 매핑**: M17.1·M17.2. 인터뷰가 "일일 체크리스트 + 에이전트 대행"으로 구체화.
- **⚠️ 플래그**: 공개=외부 노출이므로 **되돌리기(철회)·감사** 필수. 에이전트 대행 공개는 **사람 최종 확인** 게이트 유지.

### 3-3. 분석 페이지 — (M16 + Realtime 확정)
- **내용**: 앱에서 대화 종료 → AI 분석 → **대화·분석 데이터가 실시간으로 요양보호사 웹에 전송**. 이를 볼 페이지 필요.
- **반영 방식(초안)**: `session_analyses` 저장 + 웹 분석 페이지 + **Supabase Realtime 구독**(앱 종료 시 대시보드 실시간 반영). 분석 로직은 이미 만든 `core/analysis`(관찰 지표).
- **필요성·검증**: ✅ 필요. **M16(분석) + 실시간 동기화 요구**를 현직자가 확인. `core/analysis`는 이미 구현·테스트 완료.
- **기존 매핑**: M16.1(`session_analyses`)·M16.4(웹 분석 화면)·T-E3(Realtime 구독).

## 4. 보호자 페이지
- **내용**: 요양보호사가 공개(커밋)한 데이터와 **연동만**. 그 외는 1차 MVP 완성 후 개선.
- **필요성·검증**: ✅ 필요·범위 명확. M17.3(보호자=커밋 데이터만 열람)과 정합.
- **기존 매핑**: M17.3.

---

## 종합 검증 (요지)
- 인터뷰는 우리가 이미 설계한 **M16(분석 실시간)·M17(보호자 공유 커밋)·M18(AI 에이전트)** 를 **현장에서 독립 검증**해 줌 → 아키텍처 방향이 옳다는 강한 신호.
- **신규 추가 1건**: 요양일지 작성(3-1) — 현직자 1순위 요청, 스코프 상 가장 큼.
- **필수 보안 수정 1건**: 초기화면·보호자 무인증/광역 접근(2) — 선택이 아니라 반드시.
- **공통 주의**: 보호자 대상 "건강 분석" 및 일지 민감정보는 **비의료 프레이밍 + 동의·RLS·감사** 준수.
- **미결정(사용자 확정 대기)**: 보호자 본인확인 수준 · QR vs 요청 승인 방식 · 일지 사진 OCR 방식 · AI 에이전트 깊이(버튼식 v1 / 대화형 v1.5).
